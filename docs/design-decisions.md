# 设计决策记录

记录项目里每个关键技术选择的**备选方案、选择理由和已知代价**。
写这份文档的目的是让每个决策都能被追问：不是"照着教程这么写的"，而是"在什么约束下做了什么权衡"。

---

## 1. 引用溯源：代码强制输出，而不是依赖 LLM 自觉标注

**决策**：检索到的 chunk 的 `source / page / chunk_id`，由代码在回答之后无条件打印；
system prompt 里同时要求 LLM 在正文中标注 `[资料N]`，但不作为引用信息的唯一来源。

**备选方案**：只在 system prompt 里要求"回答末尾必须列出引用来源"，然后直接展示 LLM 的输出。

**为什么这样选**：LLM 的输出是概率性的，prompt 约束是"软约束"——同一个 prompt，模型可能这次老实标注、
下次漏标或标错。而"回答必须可溯源"是这个系统的核心承诺，不能建立在一个不保证生效的机制上。
把引用来源的输出放在代码里，等于用确定性的工程手段兜底不确定的模型行为：
无论 LLM 怎么发挥，用户一定能看到这次回答实际检索到了哪些文档的哪些位置。

**代价 / 已知局限**：代码打印的是"检索到的全部 top-k chunk"，不是"LLM 实际使用的 chunk"——
如果 LLM 只用了其中 2 条，另外 3 条也会被列出来，引用列表比实际使用的更宽。
真正的"引用准确率"需要评测集来量化（Phase 2），届时可以考虑只展示 LLM 声明引用过的条目。

## 2. Phase 1 手写 pipeline，不用 LangChain / LangGraph

**决策**：loader / chunker / embeddings / retriever / generator 全部自己实现，框架留到后续阶段。

**备选方案**：直接用 LangChain 的 `RetrievalQA`，几十行代码就能跑通同样的功能。

**为什么这样选**：两个原因。一是**可解释性**——框架会把 chunking 策略、prompt 拼接、检索参数都封装进
默认值里，用起来快，但出了问题（检索不准、答非所问）很难定位是哪一层的问题，也讲不清楚每一步在做什么。
二是**可替换性**——底层流程自己实现之后，框架就变成了一个"可选的工程层"，而不是项目的地基；
以后要换 LangChain、LlamaIndex 或者别的编排框架，替换的是外层，核心逻辑不用重写。

**代价 / 已知局限**：开发速度比直接用框架慢，而且像多轮对话记忆、工具调用这类框架自带的能力，
现在都没有，要用得自己实现。

## 3. 向量库：Phase 1 用 Chroma，不是 Qdrant / Milvus

**决策**：用 `chromadb.PersistentClient` 做本地持久化向量库。

**备选方案**：Qdrant（需要单独起服务或用云端实例）、Milvus（更重，偏大规模生产场景）、
或者干脆不用向量库、自己算余弦相似度。

**为什么这样选**：MVP 阶段的瓶颈是"能不能快速跑通全链路"，不是"能不能扛住百万级向量"。
Chroma 一行 `PersistentClient(path=...)` 就能用，不需要额外部署服务，本地文件即数据库，
对"面试官 clone 下来能一键复现"这个目标也更友好。
数据量只有几百个 chunk 时，Chroma 和 Qdrant 的检索性能差异不构成选型理由。

**代价 / 已知局限**：Chroma 在大规模数据量和分布式部署场景下不如 Qdrant/Milvus；
如果后续要展示工程化能力（独立服务、水平扩展、更丰富的过滤查询），需要迁移到 Qdrant。
因为检索逻辑已经封装在 `ChromaRetriever` 里，迁移时改动范围可控。

## 4. Embedding：Phase 1 用 Chroma 内置 onnx MiniLM，不是 bge-m3 或 API embedding

**决策**：使用 Chroma 默认的 `DefaultEmbeddingFunction()`（onnxruntime 版 all-MiniLM-L6-v2），
并把它单独封装在 `embeddings.py` 一个文件里。

**备选方案**：bge-m3（中英文效果更好，但模型更大、需要本地算力）、
OpenAI / Qwen 的 API embedding（效果好，但每次建索引都要花钱、依赖网络）。

**为什么这样选**：Embedding 模型和 LLM 是两个**互相独立**的组件，可以分开选型。
Phase 1 的目标是验证链路能跑通，用一个免费、无需 API key、自动下载（~79MB）的轻量模型足够；
把它单独封装成一个模块，是为了让"以后换模型"成为改一个文件的事，而不是全项目搜索替换。

**代价 / 已知局限**：MiniLM 对中文和专业术语的区分度不如 bge-m3，
技术文档里的缩写、专有名词召回可能不稳定——这也正是 Phase 2 要引入 BM25 混合检索的原因之一。

## 5. 分块策略：按段落装箱到 800 字符

**决策**：以 `\n\n` 切段落，贪心合并至 ≤800 字符封块；无段落分隔时按 `\n` 切，
单段超长时强制硬切。

**备选方案**：整页一块（语义稀释）、单句一块（语义碎片化）、
纯按固定字符数切分而完全不看段落边界。

**为什么这样选**：段落是天然的语义单元，装箱能在保留上下文的同时控制块大小。
两个极端都不可取：整页一块时，一个向量要代表整页的混合语义，
针对某个局部细节的提问会因为信号被其余内容稀释而检索不到；
单句一块时，句子里的指代（"这种方法""在此基础上"）失去上下文，
即使检索命中，LLM 拿到的也是一句读不懂的话，答案还可能横跨多个 chunk 被拆散。
800 是这两者之间的经验折中值。

**代价 / 已知局限**：800 这个数字目前是**未经实验验证的经验默认值**，
Phase 2 需要用评测集分别跑 500 / 800 / 1500，对比 Top-k 命中率和引用准确率来确定。
另外，"纯按字符硬切"虽然作为**主策略**被否决，但仍作为**最后兜底**保留：
PDF 提取出的文本经常整页没有任何空行，一段就是几千字符，
此时没有任何语义边界可用，只能按字符切——这会破坏语义完整性，
是明知有损但必须接受的退路。

## 6. Streamlit：建索引做成显式按钮，而不是选完文件自动触发

**决策**：用 `st.button("建立索引")` 手动触发，文件选中本身不执行任何索引动作。

**备选方案**：检测到 `st.file_uploader` 返回非空就自动建索引。

**为什么这样选**：Streamlit 的运行模型是**每次交互都从头重跑整个脚本**，
没有"事件监听"这一层。如果建索引写在"选中文件"这个条件下，
那么用户之后在提问框里每敲一个字、每点一次按钮，脚本重跑时都会满足这个条件，
导致同一批文件被反复重新解析和 embedding——既慢又完全是无用功。
做成按钮后，建库和问答被明确分离：索引只在点击时建一次，之后的提问只需要读已有的向量库。

**代价 / 已知局限**：多一次点击，交互上略啰嗦。
理论上可以用 Streamlit 的缓存（`st.cache_data` / `st.cache_resource`）来避免重复执行，
但缓存要求入参可哈希，而 `UploadedFile` 对象不能直接作为缓存 key，
需要先转成文件内容或其哈希值，不是拿来即用的方案——当前用按钮更直接也更可控。
补充一点：即使用户重复点击，也不会产生重复数据，
因为 `index_chunks()` 用 `chunk_id` 作为主键调用 `upsert`，同一个 chunk 会被覆盖而不是追加。

## 7. LLM 调用：用 openai SDK 统一对接 DeepSeek / Qwen / OpenAI

**决策**：只用 `openai` 这一个 SDK，通过切换 `base_url` 和 `model` 来适配不同厂商；
provider 配置集中在 `core/config.py` 的 `PROVIDER_CONFIG` 字典里，由环境变量 `LLM_PROVIDER` 选择。

**备选方案**：为每个厂商分别接入各自的官方 SDK。

**为什么这样选**：DeepSeek 和阿里云百炼都提供 OpenAI 兼容接口，这意味着一套调用代码可以覆盖三家；
把差异（base_url / 模型名 / 环境变量名）收敛到一个字典里之后，换厂商只需要改 `.env` 里的一行，
不需要动任何业务代码。这对"国内求职优先 DeepSeek/Qwen，但演示时可能需要切换"的场景很实用。

**代价 / 已知局限**：只能用到各厂商中与 OpenAI 兼容的那部分能力，厂商专有的特性
（比如某些独有的参数或接口）用不了。目前项目没有用到这类特性，所以代价可以接受。

## 8. 错误处理：返回提示信息，而不是向上抛异常

**决策**：`generate_answer()` 捕获缺少 API key（`RuntimeError`）和请求失败（`openai.OpenAIError`），
返回一段人类可读的中文提示；文档解析失败在 `build_index.py` / `parse_docs.py` 里按单个文件 try/except 跳过。

**备选方案**：让异常直接抛到最外层，由调用方（CLI 脚本 / Streamlit）各自处理。

**为什么这样选**：这个系统有两个入口（命令行脚本和网页），如果异常抛到最外层，
两边都要各写一遍捕获逻辑，而且网页端一旦漏了，用户看到的就是一整屏 traceback。
在产生错误的地方就把它转换成明确的提示信息，可以保证不管从哪个入口进来，
失败场景都是"看得懂的一句话"而不是崩溃。
单文件解析失败之所以要跳过而不是中断，是因为批量建索引时，
一个损坏的 PDF 不应该让另外几十个正常文档也白跑一遍。

**代价 / 已知局限**：用返回值传递错误，调用方无法用类型区分"这是正常回答"还是"这是错误提示"——
如果后续要按错误类型做不同处理（比如失败重试、错误率统计），需要改成结构化的返回值
（例如返回 `{"ok": bool, "answer": str, "error": str}`）。

## 9. 前端直接 import 后端模块，而不是通过 HTTP 调用（已知技术债）

**决策**：`frontend/streamlit_app.py` 通过 `sys.path` 直接 import `backend/app/rag/` 下的模块，
FastAPI 目前只有 `/` 和 `/health` 两个占位路由。

**备选方案**：把检索和问答封装成 REST API，前端通过 HTTP 调用后端。

**为什么这样选**：Phase 1 是本地单机场景，直接 import 少一层网络调用、少一层序列化，
调试更快，也省掉了为 MVP 设计 API schema 的成本。

**代价 / 已知局限**：这是明确的技术债，不是最终形态。
现在的结构不是真正的前后端分离——后端服务并没有对外提供 RAG 能力，
前端也无法部署在与后端不同的机器上。docker-compose 里 frontend 容器
之所以要挂载整个项目目录，就是这个设计导致的。后续迭代会把 RAG 逻辑
封装成 `/api/documents` 和 `/api/chat` 两个接口，前端改为 HTTP 调用。

## 10. 测试：mock 掉 LLM 调用，而不是打真实 API

**决策**：`tests/test_generator.py` 用 `unittest.mock.patch` 替换掉 `OpenAI` 客户端，
分别模拟"正常返回"和"抛出 `openai.OpenAIError`"两种情况。

**备选方案**：测试时真实调用一次 DeepSeek API。

**为什么这样选**：单元测试要验证的是**自己写的逻辑**（try/except 有没有生效、返回值对不对），
不是"DeepSeek 的服务在不在线"。打真实 API 会让测试变慢、要花钱、需要在 CI 里配置密钥，
而且网络抖动会导致测试随机失败——一个会随机失败的测试，很快就会被所有人忽略。
mock 之后，测试在 CI 里毫秒级完成，且能精确构造"接口报错"这种真实环境下很难复现的场景。

**代价 / 已知局限**：mock 测不出真实接口的行为变化（比如厂商改了返回结构、模型名下线）。
这类问题需要靠真实运行来发现——目前是靠 `scripts/ask.py` 手动验证，
后续可以考虑加一个不进 CI 的 smoke test，需要时手动跑。

## 11. 评测切块：以 canonical text 偏移为依据，不以 chunk_id 为证据锚点

**决策**：研究评测链路只切分经过哈希校验的 canonical text。每个 chunk 保存相对于该
canonical revision 的 `start_char / end_char`，偏移采用零基半开区间，单位是 Unicode 码点
（等价于 Python `str` 下标，不是 UTF-8 字节或字形簇）。chunk 不跨页，并强制满足：

```python
chunk.text == canonical_text[chunk.start_char:chunk.end_char]
```

**为什么这样选**：改变 chunk 大小、段落策略或 overlap 后，chunk 的编号和边界都会变化；
如果金标准证据直接引用 chunk_id，切块消融会让标注失效。原文字符区间属于冻结语料，
可以稳定映射到任意一次切块结果，也能用自动断言发现坐标错位。

**chunk_id 的语义**：继续使用 `{source}_p{page}_{index}`，便于展示和向量库去重；
但 `index` 依赖当前切分参数，因此 chunk_id 不是跨实验稳定标识，严禁用作金标准证据锚点。

**兼容边界**：`chunk_pages(RawPage)` 仅服务于未进入冻结语料的交互式上传 MVP；
正式评测必须使用 `load_canonical_document()` 后调用 `chunk_canonical_document()`。
